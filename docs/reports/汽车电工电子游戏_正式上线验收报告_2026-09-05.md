# 汽车电工电子游戏正式上线验收报告

检查日期：2026-09-05  
检查对象：当前工作区代码、本地运行版本、学习任务1与学习任务2教材扫描件、已梳理的学习任务2—9游戏化课程地图  
检查定位：面向中职学生、教师和系统管理员正式使用的教学互动游戏  
修订说明：根据项目既定定位，本报告不再把“游戏关卡未按教材章节名称和先后顺序编排”视为问题。教材用于确定必须掌握的知识与技能边界；游戏按照学生认知成长、工作过程和互动反馈逻辑重新组织学习过程。

## 一、最终结论

**验收结论：不通过正式上线验收；可保留为单机演示和小范围封闭试教版本。**

当前版本的优点是：任务0—2主流程已能运行，学习任务1、2没有机械照搬教材页面，而是采用维修工作情境、操作反馈和逐步支架组织学习，这一课程重构方向是正确的；工程构建、类型检查、代码规范检查及51项自动化测试全部通过，桌面宽屏视觉风格也较统一。

但“能运行”不等于“能上线”。当前存在以下上线阻断项：

1. 所有认证、进度和管理员接口缺少可信的服务端登录会话与权限校验，存在匿名读取、修改学生进度和执行管理员操作的风险。
2. 密码明文保存，代码内置并展示默认管理员账号密码；学生、教师、管理员三类角色没有真正建立。
3. 没有教师—班级—学生关系模型，无法实现“教师只能看到自己任教班级学生”的数据隔离。
4. 云端部署配置未启用数据库，账号数据写本地 JSON 文件，并硬编码开发电脑路径；多实例、并发和重启后的可靠性均不成立。
5. 手机竖屏和小屏横屏实测严重破版；平板横屏仍存在关键操作隐藏在内部滚动区、触控热区过小的问题。
6. 安全用电微实验存在“先模拟触碰带电相线，再加绝缘措施”的通关脚本，容易形成错误动作记忆。
7. 完成关卡即固定记为100分并显示“认证通过”，不能支撑教师评价、学情诊断或教学质量判断。

在P0问题全部修复、P1重点问题闭环并完成真实学生试用前，不应部署给全校师生正式使用。在“教材知识技能目标—游戏任务—行为证据—评价方式”覆盖矩阵和专业教师审定尚未完成前，页面也不应继续使用“符合中职汽车专业教学大纲标准”“认证通过”等无充分证据支撑的表述。这里要求的是可验证的目标覆盖，不是要求关卡与教材同名、同序。

## 三、P0：正式上线阻断问题

### P0-01 所有后台接口缺少服务端认证与授权

**现状与证据**

- `app/api/admin/route.ts:5-10,111-184`未校验Cookie、Session或Authorization；GET可列出全部学生，POST可重置进度、重置密码、删除账号。
- `app/api/progress/route.ts:5-23,33-58`直接信任请求中的`username`和客户端提交的完整`progress`；可读取或覆盖任意账号进度。
- `app/api/auth/route.ts:100-129`可按任意用户名查询用户资料和进度；登录成功后不创建可信服务端会话。
- 前端是否显示管理大屏仅依赖客户端`isAdmin`，见`src/components/CourseMapLobby.tsx:53-55,150-160`。

**解决方案**

1. 建立服务端Session：使用HttpOnly、Secure、SameSite Cookie；会话存储在数据库，支持过期、登出失效和管理员强制下线。
2. 建立统一授权中间层，不允许各API自行判断。任何接口先认证，再按角色和数据归属授权。
3. 学生进度写入接口只接受“本次动作或关卡提交”，由服务端计算可接受的状态；禁止客户端整体覆盖成绩、解锁状态和教师模式。
4. 管理员敏感操作加入操作审计、二次确认、幂等键和必要的速率限制。

**验收标准**

- 匿名访问全部受保护API均返回401。
- 学生访问他人进度、教师访问非任教班学生均返回403且不泄露对象是否存在。
- 客户端伪造`role`、`teacherMode`、`score`、`username`均不能越权。

### P0-02 密码与默认账号严重不安全

**现状与证据**

- `src/server/userStorage.ts:9-16,56-70`明文保存和比较密码，内置`admin/admin123`、`guest/guest123`。
- `src/components/auth/AuthDialog.tsx:39-42`管理员表单预填默认账号密码。
- 管理员重置密码会默认改为`123456`并在响应中明文返回，见`app/api/admin/route.ts:147-164`。

**解决方案**

- 使用Argon2id或bcrypt保存密码哈希；数据库中不得保留可还原密码。
- 移除所有默认生产凭据和前端预填密码；首次管理员通过部署密钥或一次性邀请创建。
- 重置密码改为一次性临时凭证/重置链接，首次登录强制改密；旧会话全部失效。
- 加入密码强度、登录失败限速、短时锁定和异常登录审计。

**验收标准**

- 代码、构建产物、接口响应、日志和数据库中均无明文密码。
- 默认账号无法登录正式环境；连续错误登录被限速并产生审计记录。

### P0-03 没有教师—班级—学生数据模型和关系授权

**现状与证据**

- 用户角色只有`student | admin`，没有`teacher`，见`src/server/userStorage.ts:9-16`。
- 只有可自由填写的`className`字符串，没有教师任教班级表、学生归属表和访问范围。
- UI中的“教师管理通道”实际只登录管理员；学生注册可任意填写班级，实测默认值为“24新能源1班”。

**解决方案：建议最小数据模型**

- `users(id, school_id, username, password_hash, role, status, created_at, updated_at)`
- `classes(id, school_id, name, grade, cohort_year, status)`
- `teacher_class(teacher_id, class_id, course_id, valid_from, valid_to, status)`
- `student_class(student_id, class_id, valid_from, valid_to, is_current)`
- `course_versions(id, course_code, version, published_at, status)`
- `learning_attempts(id, student_id, class_id, course_version_id, level_id, started_at, completed_at, score, status)`
- `learning_events(id, attempt_id, event_type, payload, occurred_at)`
- `audit_logs(id, actor_id, action, target_type, target_id, result, occurred_at, ip_hash)`

不要在学生记录上只放一个`teacher_id`。一个班可能有多位任课教师，教师也可能任教多个班。学生数据访问权应通过`teacher_class + student_class`实时推导；教师调课、转班和共同授课才有可追溯性。

**权限矩阵**

| 操作 | 学生 | 教师 | 系统管理员 |
|---|---|---|---|
| 查看学习数据 | 仅本人 | 仅当前授权任教班级 | 全部 |
| 写学习进度 | 仅本人有效会话，经服务端判定 | 不直接改原始进度，可写评语/复核 | 可纠错但必须审计 |
| 班级管理 | 无 | 查看被分配班级，不得自行认领 | 创建、停用、分配教师 |
| 用户管理 | 修改本人有限资料/密码 | 修改本人有限资料/密码 | 创建、停用、重置普通账号 |
| 导出数据 | 仅本人报告 | 仅任教班级且字段最小化 | 按授权导出全部 |

教师“选择任教班级”必须从管理员预先授权的班级列表中选择，不能自行输入或认领任意班级。学生归班采用管理员批量导入、班级邀请码加教师审核，或学籍系统同步；禁止把自由文本班级名直接作为授权依据。

### P0-04 当前持久化方案不能用于云端或多教师并发

**现状与证据**

- `.openai/hosting.json:1-4`中`d1`和`r2`均为空。
- `src/server/userStorage.ts:1-3,24-51`使用Node文件系统并硬编码开发电脑绝对路径。
- `src/server/userStorage.ts:128-163`使用单个JSON文件“读取—修改—整体写回”，无事务、文件锁、版本冲突或原子替换；写失败后静默退化到进程内存。

**解决方案**

- 若继续部署在Sites/Cloudflare Workers，使用D1保存关系数据；不要依赖本地文件系统。
- 所有账号、班级、任教关系和学习记录通过数据库事务写入；关键写操作加唯一约束、外键、版本号或乐观锁。
- 建立迁移、自动备份、恢复演练、数据导出和保留期限。
- 删除硬编码开发路径，不在源码中暴露个人电脑目录。

**验收标准**

- 两名教师、40名学生并发登录和提交进度无丢失、串班或覆盖。
- 服务重启、横向扩容后数据一致；写入失败明确返回错误，不允许“表面成功、实际只在内存”。

### P0-05 学生可绕过关卡并伪造成绩

**现状与证据**

- 匿名状态也能点击“演示模式”解锁全部关卡，见`src/components/CourseMapLobby.tsx:76-78,185-198`。
- 客户端`localStorage`保存身份/进度，可直接篡改；进度API又接受客户端整体提交。
- 任务1和任务2完成时固定写入100分，见`src/levels/level01/Level01Experience.tsx:39`、`src/levels/level02/Level02Experience.tsx:41`。

**解决方案**

- 演示模式只允许教师或管理员服务端授权；学生界面完全不渲染入口。
- 服务器保存已发布课程版本、前置条件和可接受状态迁移；每次关卡完成由服务端校验事件链。
- 成绩由明确评价量规计算，错误尝试、求助次数、关键安全动作、完成质量和教师复核分别记录；不应把“完成”自动等同“100分/认证”。

## 四、P1：试点前必须解决的问题

### P1-01 游戏化课程地图已经形成，但尚未落实为可验收的产品基线

**修正后的判断口径**

游戏关卡与教材章节不必同名、同序，也不应把教材目录直接电子化。正式验收应检查的是：教材要求的核心知识和技能是否完整覆盖、有没有科学性错误、先修关系是否合理、学生是否通过操作形成可观察证据、支架是否随能力增长而渐隐，以及学生能否换情境迁移。

已梳理的课程地图给出了合理的能力主线：

> 先安全 → 能看懂 → 能接通 → 会测量 → 会解释 → 会设计 → 会诊断

对应建议路线为：Sprint 0“维修中心第一天”、Sprint 1“实训车间突发事故”、Sprint 2“点亮第一盏检修灯”、Sprint 3“会变化的传感器”、Sprint 4A“万用表上岗证”、Sprint 4B“节点与回路追踪”、Sprint 5“电源为什么越带越累”、Sprint 6A“灯组改装工单”、Sprint 6B“不能直接接上的新设备”、Sprint 7“维修工位能源与过载审查”、Sprint 8“越来越暗的左前照灯”、Sprint 9“电路诊断资格考核”。其中任务4、6拆关，任务8作为从“会测量”转向“会诊断”的关键关，这些都属于合理的教学重构，不是偏离教材。

**当前真正的问题**

- `src/stores/userProgressStore.ts:59-141`仍保留“继电器、电机驱动/PWM、整车灯光联调”等占位规划，与上述已经形成的课程地图没有统一。问题不是它们没有按教材排序，而是尚未说明这些内容属于核心课程、迁移应用还是后续拓展，也无法证明教材任务2—9的目标没有遗漏。
- 当前产品没有一份机器可读或可版本化的课程配置，知识点、技能点、先修条件、允许操作、现象反馈、提示层级和评价证据容易继续写死在页面代码中。
- 目前的“完成/100分”只能证明流程结束，不能证明学生经历了“观察—假设—操作—记录—归纳—迁移—解释”的学习循环。

**修改方案**

1. 将上述课程地图确立为当前版本的课程产品基线，但允许后续专业教师基于试教证据调整；不得为了表面“符合教材”而把关卡强行改回教材目录顺序。
2. 建立“教材知识技能目标—游戏Sprint/情境—先修能力—关键操作与现象—学生行为证据—评价方式—内容版本”覆盖矩阵。一个教材目标可以分布到多个关卡，一个关卡也可以综合多个教材目标。
3. 对当前“继电器、电机驱动/PWM、整车灯光联调”等内容逐项归类：能够服务既定目标的，作为迁移情境或拓展关；超出本课程核心边界的，后移到拓展模块；不得挤占欧姆定律、仪表、电压降和综合诊断等必学能力。
4. 用配置定义元件、节点、正常参数、故障、允许操作、测量结果、提示和评价；确定性电路模型负责物理结果，安全规则引擎负责危险动作边界，AI导师只负责追问、分层提示和复盘，不得决定电路结果或关键安全标准。
5. Sprint 0明确标注为校本入门/准入模块即可；它不属于教材原有任务，但作为形成“先观察、再操作”习惯的先导关是合理的。
6. 未实现的关卡标为“规划中/原型”，不能以占位卡片暗示已经具备实训和认证能力；教师演示模式也只开放已实现且通过审定的版本。

**验收标准**

- 教材任务2—9的全部核心知识和技能目标均能在覆盖矩阵中追溯到至少一个游戏情境和一种有效证据；关键技能不能只用选择题代替操作。
- 任抽三个关卡，都能说明“为什么此时学、依赖什么先修能力、学生做什么、看到什么、如何证明学会、如何换情境迁移”。
- Sprint 4A/4B、6A/6B的拆分和Sprint 8的关键诊断地位得到专业教师审定；Sprint 9能形成“症状—假设—测量—证据—定位—修复—验证”闭环。
- 新增或拓展内容不得造成必学目标缺失、科学性错误或不合理的认知跳跃；课程地图和评价规则变更必须产生新版本。
- 页脚表述在审定前改为“依据《汽车电工电子基础》知识技能要求开发（试用版）”；通过目标覆盖、专业审定和试教后，才能使用更强的达标性表述。

### P1-02 安全微实验形成错误危险动作脚本

`src/levels/level01/components/ShockSimulationLab.tsx:319-395,1045-1079`要求学生先“触碰220V相线”，再“垫上10kV绝缘胶垫”才能通关；两相触电实验同样要求先双手触碰两相再戴绝缘手套。虽然数值计算与教材示例接近，但交互顺序违反“先隔离、验电、防护，再操作”的技能形成规律。

**修改建议**

- 改为“预测后果—选择防护—确认断电/验电—观察系统模拟结果”，不要求学生以危险动作为达成条件。
- 危险选项可以点击观察后果，但不能显示为“探究达标”的必经步骤；反馈必须明确“仅为仿真，现实中严禁尝试”。
- 使用事故回放或透明人体电流路径动画替代第一人称执行危险动作。

### P1-03 急救内容尚未完成专业审定，不能作为技能认证

- `src/levels/level01/firstAidConfig.json:2`仍标记`PENDING_PROFESSIONAL_REVIEW`。
- 100—120次/分、5—6厘米、30:2与教材及当前权威指南大体一致；但游戏未形成完整的AED取用/使用流程，按压位置表述也应统一为“胸部正中、胸骨下半部”等标准教学口径。
- 当前仅要求6次按压即可完成练习（`firstAidConfig.json:10`），只能作为节奏体验，不能证明学生具备CPR技能。

**修改建议**

- 请持证应急救护培训师对触电救援、呼吸判断、呼救/AED、按压、人工呼吸和停止条件逐项签审。
- 将屏幕练习定位为“知识与决策模拟”；真正技能成绩必须来自人体模型实操，由教师录入或复核。
- 支持教师选择学校采用的急救口径版本，并记录内容版本与审定人。

### P1-04 评价结果失真，无法支撑教学决策

当前任务1配置明确`scoring: false`，但学生完成即固定100分，课程大厅和后台均显示“认证通过/成绩合格”。这会把“流程走完”误报成“能力达标”。

建议采用两层结果：

1. **系统形成性证据**：关键动作顺序、危险误操作、提示次数、重试次数、完成时长、概念题、接线错误类型。
2. **教师终结性评价**：实物接线、工位整理、团队协作、CPR模型操作、口头解释；支持量规评分、评语和复核。

学生端显示“已完成/待教师评定/已达标”，不要直接显示100分；后台应能查看证据而非只有三个关卡分数。

### P1-05 团队协作、教师评价和安全文明操作未形成教学闭环

不要求照搬教材评价表，也不要求每个游戏关卡都强制组队。但团队协作、安全文明操作和教师实操评价属于中职技能形成的重要目标，应在适合的教学活动中形成可观察证据。教材任务1、2提供了自评、小组评价、教师评价和安全文明操作等要求；任务2还要求学生对照电路图连接、运行并检查。当前主要是个人点击流程，没有小组角色、教师评价入口、工位整理检查、实操证据上传/扫码确认或教师复核。

建议最小实现：每次教学活动建立`teaching_session`；教师分组并分配“操作员、监护员、记录员”；学生完成游戏后进入“待实操”；教师用量规快速勾选并签审，最终形成“游戏过程证据 + 实操评价”。

### P1-06 多账号教学后台功能不完整

正式教学至少需要：

- 管理员：创建/停用教师，创建班级，批量导入学生，分配教师任教班级，转班/毕业，重置凭据，审计查询。
- 教师：只查看授权班级；班级切换、学生搜索、任务布置、截止时间、完成率、困难点分布、学生个体过程记录、评语/复核、受控导出。
- 学生：首次激活、改密、查看个人任务和反馈；不能自由填写班级，不能看到教师模式或后台接口。

当前后台只有“全部班级/班级筛选、三个任务分数、重置/删除/导出”，且是管理员全局视图，不能满足上述流程。

### P1-07 响应式布局在手机和小屏设备上不可用

真实浏览器检查结果：

- 390×844竖屏：标题和场景文字被压成逐字换行，接线画布不可见，底部栏产生横向滚动。
- 844×390横屏：接线工作区几乎只剩标题，核心画布和操作按钮不可见。
- 1024×768横屏：基本可见，但“通电测试/闭合开关”位于内部滚动区下方，首次进入时看不到；顶部标题、进度、用户和退出按钮拥挤。

**修改建议**

- 明确支持矩阵：正式版至少支持1366×768桌面和1024×768平板横屏；如不支持手机，进入时给出明确旋转/设备提示，而不是显示破版页面。
- 取消多层滚动；关键操作条固定在场景面板底部，任何视口首屏都能看到“当前任务 + 主要操作 + 反馈”。
- 平板宽度下收起导师为抽屉、压缩顶部信息、隐藏内部英文状态。

### P1-08 接线端子与多个控件不适合触控和键盘

- 端子使用SVG`<g onClick>`，视觉半径只有9，且没有`role="button"`、`tabIndex`、键盘处理和可读名称，见`WorkbenchWiringScene.tsx:300-334`。
- 1024×768实测多个常用按钮高度只有28或38像素；原理图关闭按钮16×16；端子随画布缩放后更小。
- W3C WCAG 2.2的AA级最小指针目标为24×24 CSS像素；用于学校触控屏建议按44×44设计。

**修改建议**

- 每个端子增加至少44×44透明命中区、可见焦点、选中状态、`role=button`、`tabIndex=0`、Enter/Space连接，并提供“端子列表选择”的等效操作。
- 所有常用触控按钮不小于44×44；危险操作与普通操作保持足够间距。
- 使用自动化无障碍检查加人工键盘遍历测试。

### P1-09 信息密度、字号和动画不利于中职学生持续操作

- 任务页同时出现顶部进度、场景标题、导师卡、当前任务条和底部工具栏，关键动作被多层信息稀释。
- 相关页面存在大量9—12像素文字和`SEMI GUIDED`、`WORK ORDER`、`BUILD DOUBLE WIRE CIRCUIT`等非必要英文内部状态。
- 项目大量使用`pulse/ping/smoke/flow`循环动画，但未发现`prefers-reduced-motion`适配或全局“减少动画”设置。

**修改建议**

- 学生操作文字正文默认不小于16px，常用标签不小于14px；技术符号可保留英文，流程状态改用中文。
- 每屏只突出一个学习目标和一个主要动作；导师提示按需展开。
- 保留电流流动等教学必要动画，装饰性闪烁默认减弱；支持系统`prefers-reduced-motion`和应用内“减少动画/静音”。

### P1-10 缺少数据合规和上线运维闭环

学生姓名、学号、班级和学习记录属于个人信息。正式使用前至少完成：隐私告知、处理目的和范围、最小化收集、账号与权限审批、传输/存储加密、备份、访问审计、保留期限、删除/更正流程、安全事件响应、教育移动应用备案适用性判断、等保与ICP备案评估。

不能把CSV/Excel全班导出作为无约束功能；导出需按角色和任教范围过滤、记录审计、设置字段最小化和水印/有效期。

## 六、建议实施顺序（交给Gemini时按此拆分）

### 阶段1：先封堵安全风险

3. 封闭admin/progress/auth接口，删除默认凭据和硬编码路径。
4. 增加匿名、横向越权、纵向越权、CSRF、伪造成绩和并发写入测试。

### 阶段2：建立多教师与班级关系

3. 所有教师查询在服务端强制加入班级归属条件，不接受前端传入的任意教师/班级作为授权依据。
4. 完成转班、调课、共同授课、停用账号和历史记录保留规则。

### 阶段3：补齐三端教学流程

1. 重做系统管理员后台。
2. 新建教师工作台：班级、布置、学情、过程证据、评价、导出。
3. 重做学生注册/激活，不允许自由填写班级。

1. 以已梳理的任务2—9课程地图为基线，建立可版本化的知识技能覆盖矩阵；允许跨章节重组，不要求游戏关卡与教材一一同序。

4. 重构触电微实验危险动作顺序；完成急救持证人员审核并加入AED口径。

6. 修复响应式布局、触控热区、键盘操作、字号和减少动画设置。

- 教材决定“学什么”，游戏重新设计“怎么学”；不得以整改名义把产品改成教材翻页、知识点讲解加选择题。

- 危险错误由规则引擎阻止并展示后果；非危险错误允许发生并留下诊断证据。
- 数字表和整洁数值用于入门，真实波动和复杂故障用于进阶；公式不是通关入口，操作、解释和迁移才是核心证据。
- AI导师不能生成或修改关键安全标准，不能决定电路物理结果，不能替学生完成诊断。

## 七、必须新增的验收用例

1. 教师A任教1班，教师B任教2班；A不能通过页面、接口、修改URL/参数或导出看到2班任何学生。
2. 同一班两位共同授课教师均可查看；撤销其中一人任教关系后立即失去访问权。
3. 学生转班后，新班教师按学校规则看到允许的记录，原班教师不再看到当前数据；历史审计可追溯。
4. 学生不能打开教师演示模式、不能改分、不能解锁前置未完成关卡。
5. 匿名调用所有管理和进度API均失败；伪造角色、用户名、班级ID均失败。
6. 40名学生同时提交关卡，记录不丢失、不覆盖、不重复计分。
7. 数据库短暂失败时前端明确提示且可安全重试，不产生“显示完成但后台无记录”。
8. 390×844如不支持，显示明确设备提示；1024×768和1366×768所有主操作无需隐藏式内部滚动即可完成。
9. 所有接线端子可用触摸、鼠标和键盘完成；焦点顺序清楚，反馈可被辅助技术读取。
10. 学生完成游戏后只显示形成性结果；教师完成实操评价后才显示“达标/认证”。
11. 教材任务2—9的每个核心知识、技能目标都能追溯到已发布关卡、学生行为证据和评价规则；不以关卡名称、章节顺序相同作为通过条件。
12. 对任一已发布关卡随机更换一个负载、故障点或接法后，系统返回的现象和测量结果仍符合电工规律，学生必须重新依据证据完成判断。
13. 同一能力在引导、标准和挑战模式中提示逐步减少；学生在新情境中仍能独立完成，才计入迁移达成。
14. 继电器、PWM等拓展内容明确标注其依赖的核心能力和课程层级，不得替代欧姆定律、仪表使用、电压降和综合诊断等必学内容。
