# 汽车电工电子游戏二阶段修改后账号与教学组织复验报告

复验日期：2026-09-05  
复验对象：Antigravity完成阶段1、阶段2修改后的当前工作区代码和本地运行版本  
复验重点：学生、教师、系统管理员登录分流；账号生命周期；班级管理；任教关系；学生归班；数据隔离；正式部署可靠性  
后续执行：由Codex按本报告的优先级和验收用例分包实施；先修P0，再完善系统管理员后台，未经整体复验不得直接进入后续功能开发  

## 一、复验结论

**阶段1、阶段2只能判定为“部分完成”，账号与教学组织功能不通过正式使用验收。**

当前版本已经完成密码哈希、服务端Session、三类角色字段、班级表、教师任教关系表、学生归班表以及部分服务端读取隔离；68项自动化测试、类型检查、代码规范检查和构建均通过。这说明底层改造不是完全无效。

但目前的产品仍把“任课教师”和“系统管理员”混在同一个登录入口、同一个后台组件和同一组管理接口里。系统管理员实际看到的仍是“全校学情大屏”，没有完整的教师账号、学生账号、班级和任教关系管理界面。更严重的是，退出登录没有注销服务端会话，教师写入他人进度时缺少跨班校验，学生仍可自由填写班级，生产环境仍使用本地SQLite文件且自动生成固定测试账号。

因此，不建议继续开发后续普通功能。应先返工账号和教学组织模块，完成本报告P0、P1项目后，再进入下一阶段。

## 二、已经完成且可以保留的部分

1. `users`已支持`student / teacher / admin`三类角色，密码使用scrypt哈希。
2. 已建立HttpOnly Session Cookie、登录限速、会话撤销和操作审计底座。
3. 已建立`classes`、`teacher_class`、`student_class`、`learning_attempts`和`learning_events`等基础表。
4. 教师读取学生名单和学习进度时，服务端能够按任教班级过滤；共同授课、撤销任教和学生转班已有基础服务逻辑。
5. 教师登录后实测只能看到24新能源1班的1名学生；系统管理员登录后可以看到两个班的学生，说明读取隔离主链条已经起步。
6. 自动化检查通过：7个测试套件、68/68项测试通过；`typecheck`、`lint`和`build`均通过。

这些成果应在返工中保留，不需要推倒数据库和认证底座重做。

## 三、P0：必须立即修复的安全和数据问题

### P0-01 前端“退出”没有注销服务端Session

`src/stores/authStore.ts:130-133`的`logoutUser()`只清除localStorage和前端进度，没有调用已经存在的`POST /api/auth { action: 'logout' }`。`src/components/CourseMapLobby.tsx:164-173`直接调用这个同步函数。

这意味着用户看到“已经退出”，但HttpOnly Cookie对应的服务端会话仍可能有效。在公用实训室电脑上，下一个使用者存在继续复用原教师或管理员会话的风险。本次实测点击前端“退出”后，随后访问`GET /api/auth`仍返回200，验证了服务端会话没有被注销。

**解决方案**

- 将退出改为异步服务端登出：先调用`POST /api/auth/logout`撤销当前Session并清Cookie，再清理前端状态。
- 即使网络异常也清理本地状态，但必须提示“服务器会话注销失败”，并在下一次启动时重新向服务端核验。
- 增加“退出后再次访问所有受保护API均返回401”的真实浏览器测试。

### P0-02 教师可向非任教班学生写入学习进度

`app/api/progress/route.ts:154-187`在写入其他用户名时只拦截学生角色；教师查到目标用户后即可继续写入，没有像读取路径`78-98`那样调用`isTeacherAuthorizedForStudent()`。

现有测试只覆盖教师跨班读取，没有覆盖教师跨班写入，所以68项测试全通过不能证明这里安全。

**解决方案**

- 最稳妥方案：教师不得通过学生进度接口写入任何学生的原始游戏进度。教师评价、评语、实操成绩使用独立的`teacher_evaluations`接口和数据表。
- 如果确需教师代为重置某次学习尝试，必须通过专用动作接口，校验任教关系、记录原因和审计，不能提交整份`progress`覆盖数据。
- 学生进度接口只允许学生写本人，并由服务端接受单次事件或状态迁移；禁止客户端整体覆盖成绩和关卡状态。

### P0-03 生产部署仍没有可靠数据库

`.openai/hosting.json:1-4`的`d1`、`r2`仍为空；`src/server/db/database.ts:194-203,236-240`继续把数据库保存到运行目录下的`data/app.db`。这在本地开发可运行，但不能证明在Sites/Workers多实例、重启和并发环境中持久可靠。本次启动日志还出现`sql-wasm.wasm`无法从`/bundle`读取的错误；本地随后由Node原生SQLite继续运行，并不能证明Workers环境存在同样的兜底能力。

**解决方案**

- 如果正式部署在当前Sites/Cloudflare环境，接入D1并建立可重复迁移；如果改用独立服务器，则选择受支持的事务数据库，不要继续把sql.js文件当生产数据库。
- 完成备份、恢复、并发写入、跨实例一致性和迁移回滚测试。

### P0-04 正式环境会自动生成固定测试账号和密码

`src/server/db/bootstrap.ts:14-70`写死`admin`、`teacher`、`teacher1`、`teacher2`、`student1`、`student2`及固定密码；数据库初始化会自动创建这些账号。`teacher`和`teacher1`还是同一教师的重复账号。

**解决方案**

- 测试种子仅允许在`development/test`环境显式启用，生产环境禁止运行。
- 首个系统管理员通过一次性部署凭证创建，首次登录强制改密。
- 删除重复教师身份；一个自然人原则上只对应一个账号。

### P0-05 学生自行注册仍可自由填写班级，且没有建立真实归班关系

`src/components/auth/AuthDialog.tsx:25-31,209-229`让学生自由填写“所属班级”；`app/api/auth/route.ts:35-89`仅把班级名称写入`users.class_name`，没有写入`student_class`。

结果是学生可以自称属于任意班级，但教师授权查询依赖`student_class`，出现“页面显示有班级、教师却看不到学生”或显示班级与实际授权班级不一致的问题。

**解决方案**

- 正式版取消自由文本选班。系统管理员批量导入或创建学生时直接设置班级。
- 如保留学生自助激活，只允许输入学号和一次性激活码；班级来自管理员预置记录，不由学生选择。
- `student_class`是唯一归班事实来源；`class_name`不得参与授权，建议删除或仅作为不可直接写入的展示缓存。

## 四、P1：账号和教学组织功能不完整

### P1-01 三类角色在登录界面没有真正分开

本地实测登录弹窗只有“学员登录、学员注册、教师管理通道”。所谓“教师管理通道”的表单同时写着“陈师傅/管理员专区”“管理员账号”“进入教学管理后台”。教师账号可以从这里登录，系统管理员也可以从“学员登录”入口成功登录。

登录处理函数均调用同一个`loginUser()`，没有声明或校验期望角色，见`src/components/auth/AuthDialog.tsx:46-109,118-177,264-318`。登录API返回什么角色，前端就进入什么角色。

系统管理员登录后，大厅还把其标成“指导教师”，见`src/components/CourseMapLobby.tsx:114-136`。这不是文字小问题，而是角色职责尚未设计清楚。

**目标界面**

- 学生入口：学生登录、首次激活；不提供自由注册和自由选班。
- 教师入口：教师账号登录；明确进入“教师教学工作台”。
- 系统管理员入口：独立的“系统管理登录”；进入账号与组织管理后台，不显示学生技师等级、学习进度或“指导教师”。
- 后端认证服务可以共用，但登录请求必须带`expectedRole`，服务端验证账号角色是否与入口匹配；错误提示不泄露账号实际角色。

### P1-02 系统管理员后台只是学情大屏，不是系统管理后台

实测“系统管理大屏”只有学生学情、班级筛选、导出、重置进度、重置密码和删除学生按钮。没有以下页面：

- 教师账号列表、创建、编辑、停用、恢复、重置凭据；
- 学生账号创建、编辑、批量导入、停用、恢复、转班；
- 班级创建、编辑、归档、恢复；
- 教师任教班级分配、撤销和共同授课；
- 操作审计与异常登录查询。

当前`AdminDashboard`同时服务教师和管理员，仅通过`isAdmin`隐藏几个按钮，见`src/components/CourseMapLobby.tsx:53-55`和`src/components/admin/AdminDashboard.tsx:234-289,483-528`。这种做法会不断造成权限和文案混杂。

**解决方案**

新建互相独立的页面和组件：

- `TeacherDashboard`：任教班级、学生学情、任务布置、过程证据、评价和受控导出。
- `SystemAdminConsole`：用户管理、班级管理、任教关系、学生归班、账号安全、审计日志和系统配置。

不要继续在同一个`AdminDashboard`中用条件判断堆叠两套业务。

### P1-03 管理员账号API只有零散动作，没有完整生命周期

当前API可以查询在职教师、建班、分配/撤销任教、学生转班、重置密码和软删除账号，但没有：

- 创建教师账号；
- 管理员创建/批量导入学生；
- 编辑教师或学生姓名、工号/学号等基本资料；
- 停用、恢复账号；
- 班级改名、归档、恢复；
- 查看已停用/已注销账号；
- 强制用户下线、查看最近登录和安全状态。

`delete_student`实际上只禁止删除管理员，因此传入教师用户名也可能把教师软删除，但接口名称、提示和审计都写“学生”，见`app/api/admin/route.ts:280-407`。这属于偶然可用，不是合格的教师账号管理功能。

**解决方案**

按资源拆分管理员API：

- `/api/admin/users`：列表、创建、编辑、停用、恢复、注销、重置凭据、强制下线；
- `/api/admin/classes`：创建、编辑、归档、恢复；
- `/api/admin/teacher-classes`：分配、撤销、设置有效期和课程；
- `/api/admin/student-classes`：入班、转班、毕业及历史查询；
- `/api/admin/audit-logs`：按人员、动作、时间和结果检索。

所谓“删除”默认采用可审计的注销/软删除，保留学习记录和任教历史；物理删除必须另行定义数据保留政策。

### P1-04 班级关系服务缺少对象角色和状态校验

`src/server/db/classService.ts:179-198`分配教师时没有确认目标用户确实是有效教师；`327-357`给学生分班时没有确认目标用户确实是有效学生。外键只能证明用户存在，不能阻止把管理员加入学生班级或把学生分配为任课教师。

**解决方案**

- 每次关系变更均校验用户角色、账号状态、班级状态和学校范围。
- 数据库增加唯一约束：同一教师、班级、课程同一有效期不得重复；每名学生只能有一个当前班级。
- 所有转班、撤销和共同授课操作放在事务中并写审计日志。

### P1-05 前端身份仍依赖localStorage，和服务端Session可能失步

`src/stores/authStore.ts:24-60`把完整用户角色保存在localStorage；应用启动时没有先调用`GET /api/auth`恢复和验证服务端会话。账号被停用、Session过期或管理员强制下线后，前端仍可能显示旧的教师/管理员界面，直到接口失败，而且当前多个请求对401/403没有统一处理。

**解决方案**

- 应用启动必须向服务端获取`/api/auth/me`，服务端返回的当前身份是唯一可信来源。
- localStorage最多保存非敏感的界面偏好，不保存可信角色。
- 全局处理401：清理前端状态并返回对应登录页；403显示权限不足，不能静默空白。

### P1-06 临时密码“强制修改”只有字段，没有业务流程

管理员重置密码会设置`must_change_password=1`，登录接口也会返回`mustChangePassword`，但`UserProfile`没有该字段，前端没有修改密码页面，也没有限制未改密账号继续使用系统。管理员界面还把默认重置值预填为`123456`，见`src/components/admin/AdminDashboard.tsx:172-185`。

**解决方案**

- 补充首次登录/重置后强制改密页面和`change-password`接口；修改成功撤销其他会话并清除标志。
- 不预填`123456`；生成一次性随机临时凭证，并设置短时有效、只展示一次。
- 未完成强制改密的用户只能访问当前身份和改密接口。

### P1-07 页面数据已经出现关系展示不一致

系统管理员后台实测能列出student1、student2及其所属班级，但班级下拉框同时显示两个班均为“0人”。这说明班级统计与学生列表使用的关系或刷新结果不一致。正式教学中会直接导致管理员误判班级人数。

**解决方案**

- 统一从`student_class.is_current=1`统计班级人数，禁止从`users.class_name`统计授权数据。
- 班级变更后使学生列表、班级统计和教师权限缓存同时失效并刷新。
- 增加“班级统计人数=该班当前学生列表行数”的集成测试。

### P1-08 教师和管理员仍被当成“特殊学员”处理

系统管理员登录后仍进入课程大厅，显示“完成进度0/10”“指导教师”“演示模式”和“重置学习记录”；教师账号也拥有自己的学习进度。`src/server/db/bootstrap.ts:105-123`给所有角色创建`user_progress`，`app/api/auth/route.ts:176-218`给所有角色返回学习进度，`src/stores/authStore.ts:76-84`又把它保存为当前本地学习记录。

这会把三个不同主体混成一套状态：学生是学习者，教师是教学组织者，系统管理员是账号与系统治理者。教师预览课程不等于教师本人形成学生成绩，系统管理员更不应具有“技师等级”。

**解决方案**

- 系统管理员登录后直接进入`SystemAdminConsole`，不进入学生课程大厅。
- 教师登录后直接进入`TeacherDashboard`；如需备课，使用独立“课程预览/演示”状态，不生成学生成绩和学习尝试。
- `user_progress`和正式`learning_attempts`只允许学生角色拥有；历史脏数据通过迁移清理或标记为非正式预览数据。
- 学生登录后才加载学生进度，教师、管理员认证响应不返回学生进度结构。

## 五、目标角色与权限边界

| 功能 | 学生 | 任课教师 | 系统管理员 |
|---|---|---|---|
| 登录入口 | 学生登录/激活 | 教师登录 | 独立系统管理登录 |
| 查看学习数据 | 仅本人 | 仅任教班级学生 | 全校，可审计 |
| 写游戏进度 | 仅本人，经服务端判定 | 不写原始游戏进度 | 原则上不写；纠错需专用审计流程 |
| 教学评价 | 查看本人 | 评价任教班学生 | 查看规则与审计，不代替教师评价 |
| 教师账号管理 | 无 | 仅维护本人有限资料 | 创建、编辑、停用、恢复、注销、重置凭据 |
| 学生账号管理 | 仅本人改密 | 不直接改账号；可发起协助申请 | 创建、编辑、导入、停用、恢复、注销、重置凭据 |
| 班级管理 | 无 | 查看任教班级 | 创建、编辑、归档、恢复 |
| 任教关系 | 无 | 查看本人任教关系 | 分配、撤销、共同授课、设置有效期 |
| 学生归班 | 不自选 | 查看，不擅自转班 | 入班、转班、毕业、保留历史 |
| 数据导出 | 本人报告 | 仅任教班、字段最小化 | 按管理范围导出并审计 |

教师不是“小管理员”，系统管理员也不是“权限更大的教师”。两者必须在页面、接口和业务数据上分别建模。

## 七、必须通过的验收用例

1. 系统管理员从学生入口登录时被拒绝进入学生界面；教师从系统管理员入口登录时被拒绝进入管理员后台。
